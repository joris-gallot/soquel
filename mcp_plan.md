# MCP server mode - plan

Soquel runs a local MCP server exposing the user's connections to agents (Claude Code, Cursor, ...) through the existing command layer, with UI guardrails. This is the differentiator: safe scoped DB access for agents without copying credentials into config files - tunnels and keychain are already handled by the app.

## Architecture

- **Server lives inside the app process** (tokio task), not a separate binary: it needs the pools, tunnels and keychain that the Rust core owns.
- Crate `rmcp` (official Rust MCP SDK, pure Rust), transport **streamable HTTP** bound to `127.0.0.1:<port>`. rmcp validates Host against loopback by default (DNS rebinding protection).
- Auth: **Bearer token** generated by the app, stored in the SecretStore, checked by middleware on every request. Regenerable from the UI.
- MCP tools call the same logic as the Tauri commands via the shared `AppState`: one surface, two clients (webview + agents).
- Agent side: `claude mcp add --transport http soquel http://127.0.0.1:<port>/mcp` with the token header. The UI generates ready-to-paste snippets.

## Guardrails

- **Per-connection opt-in**: new `agentAccess` field on `ConnectionProfile`: `none` (default) | `read-only` | `write-with-approval`. A connection without opt-in does not exist for agents (not listed, not connectable).
- **Read-only enforced by the engine, not by SQL parsing.** Each agent query runs on a dedicated read-only session:
  - postgres: extended protocol (single statement) inside an explicit `READ ONLY` transaction.
  - mysql: `START TRANSACTION READ ONLY` (blocks DML) + first-keyword deny-list for DDL/admin statements (DDL implicit-commits out of read-only transactions in mysql).
  - sqlite: separate handle opened with `SQLITE_OPEN_READONLY` (filesystem-level, cannot be undone by SQL).
  - redis (phase 3): allowlist of read commands.
  - mongo (phase 3): find/count/aggregate without `$out`/`$merge`; no replace/delete.
- **Visual approval for writes**: with `write-with-approval`, a non-read query emits an event to the webview; a dialog shows the exact SQL; the MCP call blocks until accept/deny (timeout = deny). Phase 2.
- **Audit log**: append-only JSONL in the app data dir: timestamp, tool, connection, query, outcome, duration, row count. Viewer in the UI.
- **Result caps** for agent consumption: row/byte limits with pagination hints; agents never need 1.5M rows.

## Tool surface (v1)

| Tool | Backing | Notes |
| --- | --- | --- |
| `list_connections` | ProfileStore | opted-in profiles only; includes kind, engine version, connected state |
| `get_schema` | `Introspect::schema_snapshot` | schemas, tables, columns, PKs, FKs, indexes |
| `get_table_ddl` | `Introspect::table_ddl` | |
| `run_query` | read-only `SqlSession` | single statement, capped results |
| `sample_rows` | `SqlQuery::table_rows` | paginated table browse without SQL |

Connections are addressed by profile id; agents may trigger `connect` on an opted-in profile (credentials stay in the core).

## Phases

**Phase 1 - core (Rust)**
1. `rmcp` + HTTP server plumbing, `mcp.rs` module, lifecycle as typed commands: `mcp_status`, `mcp_start`, `mcp_stop`, `mcp_regenerate_token`.
2. `agentAccess` on ConnectionProfile (serde default `none`), bindings regen.
3. Read-only session path per driver (postgres, mysql, sqlite).
4. Tools v1 (table above) + audit JSONL.
5. Tests: rmcp client against the seeded compose databases; per-engine proof that INSERT/DDL is rejected in read-only; token auth rejected/accepted; non-opted-in profile invisible.

**Phase 2 - guardrails UI (Vue)**
6. Settings: server toggle, port, token copy, status indicator.
7. Connection form: agent access selector + badge in the connection list.
8. Approval dialog (event + pending map + timeout deny).
9. Audit log viewer.
10. Agent config snippet generator.

**Phase 3 - polish**
11. kv/doc read tools, query cancel, caps/timeout tuning.
12. README section + landing story.

## Open questions

- Default port (fixed vs configurable-first).
- Approval granularity: per query vs per agent session.
- Should `run_query` auto-connect an opted-in but disconnected profile, or require explicit `connect`? (leaning yes, auto-connect)
